# Claude Code Harness Starter

> 새 서비스를 시작할 때 복사해 쓰는 Claude Code 하네스(규칙·스킬·에이전트)와 초기 문서 양식.
> A starter harness for Claude Code: project rules, skills, review agents, and early-stage product/design doc templates (Korean).

Claude Code에 일을 맡기다 보면 같은 실수를 여러 번 교정하게 된다. 리뷰 없이 완료라고 보고하거나, 추정을 사실처럼 문서에 쓰거나, 코드가 너무 빨리 쌓여서 내가 이해하지 못한 채 다음으로 넘어가는 식이다. 이 저장소는 그런 교정을 규칙으로 바꿔 쌓아 온 하네스에서 서비스와 상관없이 통하는 부분만 골라 낸 출발점이다.

## 핵심 아이디어

- **완료 전 독립 리뷰.** 작성자가 자기 결과를 확인하지 않는다. 맥락이 분리된 리뷰어 에이전트가 PASS/REDO를 판정한다. REDO는 최대 2번까지 하고, 그래도 안 되면 사람이 판단한다.
- **사람의 이해가 병목.** 커밋을 위험도 A(돈·상태·권한)/B(외부와의 약속)/C(반복·표시)로 나누고, 등급마다 개발자가 확인할 깊이와 다음 커밋으로 넘어가는 질문을 정해 둔다.
- **모든 사실에 근거.** 설계 문서의 코드 주장에는 `파일:라인`을, 외부 사실에는 출처와 확인 수준을 단다. 근거가 없으면 `[가정]`으로 드러낸다.
- **결정은 사람이.** 제품 결정은 문서가 대신 내리지 않는다. 선택지 / 개발 영향 / 결정 전 기본값으로 올리고, 정해진 것은 결정 기록에 남긴다.
- **하네스는 실수에서 자란다.** 처음부터 길게 쓰지 않는다. 같은 지적이 두 번 나오면 그때 한 줄을 추가한다.

## 구성

```
template/                     ← 새 프로젝트 폴더에 통째로 복사
├── CLAUDE.md                 매 세션 읽히는 공통 규칙, 폴더 지도, 하네스 라우팅
├── .gitignore
├── .claude/
│   ├── skills/
│   │   ├── review-loop/      완료 전 독립 리뷰 (PASS/REDO, 최대 3회차)
│   │   ├── dev-task/         기능·버그 작업 절차, 커밋 등급별 확인 기준
│   │   ├── design-doc/       코드 전 구현설계 작성·재검토
│   │   └── harness-change/   하네스를 언제·어디에·어떻게 바꿀지
│   └── agents/
│       ├── code-reviewer.md       읽기 전용 리뷰어 (공통 점검 13항목)
│       ├── code-investigator.md   코드 현황을 파일:라인 근거로 조사
│       └── external-researcher.md 외부 규격·규제를 출처·확인 수준과 함께 조사
└── docs/
    ├── 01-product.md         제품 한 장: 문제, 사용자, 핵심 흐름, 범위, 제약
    ├── 02-design-template.md 구현설계 양식
    ├── 03-decisions.md       결정 기록
    └── design/               실제 구현설계를 두는 곳
```

## 시작하기

**1. 복사.** 이미 있는 파일은 덮어쓰지 않는다.

```bash
# macOS / Linux / Git Bash
cp -Rn claude-harness-starter/template/. <새 프로젝트>/
```

```powershell
# Windows PowerShell (/XC /XN /XO: 이미 있는 파일 건너뜀. 종료 코드 1은 정상 복사)
robocopy claude-harness-starter\template <새 프로젝트> /E /XC /XN /XO
```

macOS의 `cp -Rn`은 건너뛴 파일이 있으면 메시지 없이 종료 코드 1로 끝난다. 폴더에 이미 `CLAUDE.md`나 `.gitignore`가 있으면 복사되지 않으니 직접 합친다. 특히 `.gitignore`의 `_workspace/`, `.env*`, `.claude/settings.local.json` 줄을 빠뜨리지 않는다.

**2. 빈칸 채우기.** `CLAUDE.md`와 `.claude/` 안의 `{{ }}` 자리를 채운다. 남은 자리는 `grep -rn "{{" CLAUDE.md .claude`로 찾는다. 모르는 칸은 지우지 말고 "미정"으로 둔다. 비워 두면 빠뜨린 것과 정하지 않은 것을 구분할 수 없다. 저장소 경로는 윈도우에서도 `D:/dev/<프로젝트>`처럼 슬래시로 쓴다.

`docs/`의 세 파일은 쓰임이 다르다.

| 파일 | 쓰는 법 |
| --- | --- |
| `01-product.md` | 그 자리에서 채운다. 미정 칸은 설계에서 "결정 필요"로 올라온다 |
| `02-design-template.md` | 복사용 양식. `{{ }}`를 그대로 두고, 설계할 때마다 `docs/design/<기능>-v1.md`로 복사해 채운다 |
| `03-decisions.md` | 그 자리에 한 줄씩 쌓는 기록. 첫 결정을 적을 때 예시 행(`D1`)을 지운다 |

**3. 제품 한 장부터.** Claude에게 "제품 한 장 같이 채우자"고 하면 질문하면서 `docs/01-product.md`를 채운다. 이후 설계와 구현은 모두 이 문서를 기준으로 삼는다.

**4. 키우기.** 처음 몇 주는 하네스를 늘리지 않는다. 같은 종류의 지적이 두 번 나오면 `harness-change` 절차(제안 → 승인 → 반영 → 리뷰 → 커밋)로 한 줄씩 추가한다.

## 필요해지면 추가할 스킬

처음부터 넣지 않는다. 그 상황이 실제로 생기면 아래 핵심 규칙을 출발점으로 `harness-change` 절차로 만든다.

| 상황 | 스킬 | 핵심 규칙 |
| --- | --- | --- |
| 기획자·동료에게 진행 상황 보고 | `status-reply` | 상태값을 문서마다 같게 쓰기, 원인을 확인하기 전에 단정하지 않기, 결정 요청은 선택지·영향·기본값으로만 |
| 외부 업체·기관과 미팅 | `meeting-prep` | 말할 문구와 내부 메모 분리, 약속하는 말 대신 "검토 후 회신", 현재 취약점·내부 논의는 말하지 않기 |
| 앱스토어·서버 배포 반복 | `release` | 빌드 번호 확인, 스토어 업로드는 매번 사람이 확인 |
| 다른 사람과 저장소 공유 | `upstream-watch` | 작업 시작 전 원격 기본 브랜치의 새 커밋을 확인하고 영향 요약 |
| 화면 설계가 잦음 | `ui-design` | 디자인 기준 문서를 먼저 읽고, 정확한 문구와 재사용 컴포넌트까지 명세 |

## 원칙

1. **규칙은 메모리가 아니라 하네스에 둔다.** 자동 메모리에는 진행 상태와 개인 맥락만 둔다. 메모리에 쌓인 규칙은 세션마다 지켜진다는 보장이 없다.
2. **규칙은 실수가 생기는 지점에 둔다.** 조사에서 틀린 사실이면 조사 에이전트에, 문서 표현이 틀렸으면 그 문서를 쓰는 스킬에 둔다. 루트 `CLAUDE.md`에 다 몰지 않는다.
3. **규칙마다 이유를 붙인다.** 이유가 있어야 애매한 상황에서도 취지대로 판단한다.
4. **일반 규범은 "알지만 시키지 않으면 건너뛰는 것"만 적는다.** 가독성이나 네이밍처럼 모델이 알아서 하는 것은 적어도 효과가 없고 문서만 길어진다. 테스트 실행, 동시성, 권한 확인처럼 직접 열어 봐야 하는 것은 적는다.
5. **도메인 체크리스트는 실제 지적에서 키운다.** 상상으로 미리 길게 쓰지 않는다.
6. **결론을 바꾸는 분기까지 읽고 설명한다.** 조기 종료, 건너뛰기, 예외·롤백을 빼고 설명하면 그 설명으로 내린 판단이 틀린다.
7. **리뷰어에게는 대상·기준·회차만 준다.** 작성자의 설명이나 판단(위험도 등급 등)을 넘기면 리뷰어가 그 틀로 읽는다.
8. **에이전트를 늘리기 전에 병목을 본다.** 혼자 개발할 때 병목은 대개 에이전트 수가 아니라 내가 이해하는 속도다.
9. **세션 여러 개가 같은 폴더의 코드를 동시에 고치지 않는다.** 필요하면 `git worktree`로 폴더를 나눈다.
