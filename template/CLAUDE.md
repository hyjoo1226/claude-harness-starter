## 반드시 지킬 것

- **기본 브랜치(`{{main}}`)에 직접 커밋하지 않는다.** 작업은 `feat/<기능>`, `fix/<내용>`, `chore/<내용>` 브랜치에서 한다. 합치기는 사용자가 결정한다.
- 커밋·push는 사용자가 요청할 때만 한다. 강제 push, 운영 DB 변경, 스토어 업로드, 외부 서비스로의 발송은 매번 사용자 확인을 받는다. 되돌릴 수 없거나 밖으로 나가는 일이기 때문이다.
- 모든 산출물(코드, 설계 문서, 보고 문서)은 완료라고 말하기 전에 `review-loop` PASS를 받는다. 작성자 혼자 검증하면 처음 놓친 가정을 다시 놓친다.
- 코드 동작을 설명할 때는 결론을 바꿀 수 있는 분기(조기 종료, 건너뛰기, 예외·롤백 처리)까지 읽은 뒤 답하고, 다 읽지 못했으면 그렇다고 밝힌다. 사용자는 그 설명을 근거로 설계를 판단하기 때문이다.
- 제품 결정(무엇을 만들지, 범위, 정책)은 사용자가 한다. Claude는 선택지와 각 선택의 개발 영향을 제시하고, 정해진 것은 `docs/03-decisions.md`에 남긴다.
- 커밋 메시지: `접두어: 내용`. 접두어는 `Feat`, `Fix`, `Test`, `Docs`, `Refactor`, `Chore`, 내용은 한국어. `Co-Authored-By` 같은 공동 작성자 줄은 넣지 않는다.

## 하네스

| 상황 | 사용 |
| --- | --- |
| 기능 개발, 버그 수정 | `dev-task` |
| 모든 산출물의 독립 검증 | `review-loop` → `code-reviewer` |
| 코드 작성 전 구현설계, 기존 설계 재검토 | `design-doc` → `code-investigator`, `external-researcher` |
| 하네스 추가·수정·정리 | `harness-change` |

같은 종류의 지적·교정이 두 번 이상 나오거나, 리뷰어가 하네스 자체의 빈틈을 짚거나, 같은 절차를 세션마다 손으로 반복하면 작업 중이라도 하네스 변경을 제안한다. 규칙은 메모리가 아니라 하네스에 두고, 변경은 `harness-change` 절차를 따른다.
