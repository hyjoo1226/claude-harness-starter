# dev-task

## 0. 사전 확인

- `git status --short`와 현재 브랜치를 확인한다. 작업은 기본 브랜치에서 갈라진 `feat/<기능>`·`fix/<내용>` 브랜치에서 한다. 무관한 변경이 있으면 건드리지 말고 사용자에게 알린다.
- 과제명을 정하고 `_workspace/<과제명>/progress.md`를 만들거나 이어서 읽는다. 단계가 끝날 때마다 "완료한 것 / 다음 할 것 / 막힌 것"을 짧게 갱신한다. 세션이 끊기거나 `/clear` 후에도 이어가기 위해서다.
- 구현설계(`docs/`)가 있으면 해당 절을 기준으로 삼는다. 설계에 없는 결정이 필요하면 코드 전에 사용자에게 묻는다.
- 변경이 여러 모듈에 걸치거나 DB 스키마·인증·결제 흐름을 건드리면, 코드 수정 전에 계획(수정 파일, 테스트, 위험)을 사용자에게 먼저 보여 주고 승인을 받는다.

## 1. 재현과 판정 (버그일 때)

| 상태 | 의미 |
| --- | --- |
| 버그 확정 | 테스트로 실제 재현함 |
| 코드상 가능성 | 코드에서 문제를 확인했으나 실제 동작은 미확인 |
| 미재현 | 같은 시나리오로 재현되지 않음 |

가능하면 실패하는 테스트를 먼저 작성해 "버그 확정"으로 만든다. 제품 정책이 정해지지 않은 항목은 고치지 말고 사용자에게 선택지와 영향을 제시한다.

## 4. 독립 리뷰

`review-loop`를 실행한다. 대상은 이번 커밋 범위나 작업 중인 diff, 기준은 요구사항이나 구현설계의 해당 절이다. 아래 등급은 사용자 확인 깊이에만 쓰고 리뷰어 프롬프트에는 넣지 않는다. PASS 전에는 완료로 보고하지 않는다.

### 4.1 커밋 등급과 사용자 확인

코드 리뷰 PASS는 등급과 상관없이 받는다. 등급에 따라 달라지는 것은 사용자가 얼마나 깊이 보는가다. 출시 후 장애를 고치는 사람은 사용자이므로, 핵심 코드를 이해하지 못한 채 다음 커밋으로 넘어가지 않는다. 다만 모든 커밋을 같은 깊이로 보면 시간이 위험한 곳에 모이지 않는다.

| 등급 | 해당 | 사용자 확인 깊이 |
| --- | --- | --- |
| A. 돈·상태·권한이 바뀜 | {{예: 결제·포인트, 주문 상태 전이, 잠금·중복 방지, 권한·인증, 데이터 삭제, 배치}} | 한 줄씩. Claude가 분기마다 짚고, 실패 시나리오 테스트가 통과하는 것을 함께 확인 |
| B. 외부와의 약속 | 공개 API 요청·응답, 웹훅, 에러 코드, DB 스키마, 외부 서비스 연동 형식 | 인터페이스(요청·응답·테이블)를 확인하고 구현부는 훑어봄. 나중에 바꾸기 비쌈 |
| C. 반복·표시 | DTO, 조회 화면, 표시, 문구 | 요약과 diff를 훑어봄 |

한 커밋에 여러 등급이 섞이면 높은 등급으로 본다. 애매하면 높은 쪽으로 정한다.

**커밋마다 사용자에게 줄 설명** (review-loop PASS 뒤, 커밋 전):
1. 무엇을 왜 바꿨는가. 구현설계의 어느 절을 구현했는가
2. 결론을 바꾸는 분기: 조기 종료, 건너뛰기, 예외·롤백, 타임아웃이 각각 어떤 상태로 끝나는가
3. 설계와 달라진 점, 미정 항목에 기본값을 적용한 곳
4. 테스트: 확인한 것과 확인하지 못한 것(예: 외부 서비스 실제 호출 없이 mock으로만 확인)

**다음 커밋으로 넘어가는 기준**
- A: 사용자가 Claude의 설명 없이 세 질문에 답할 수 있다. ① 중간에 죽거나 타임아웃 나면 돈·데이터·상태는 어떻게 남는가 ② 같은 요청이 두 번 오면 무엇이 막는가 ③ 잘못됐을 때 어디서 알아채고 어떻게 복구하는가
- B: ① 다른 개발자(또는 앱)가 문서만 보고 붙일 수 있는가 ② 이 필드·컬럼을 나중에 바꾸면 무엇이 깨지는가
- C: 사용자가 요약을 읽고 이의가 없다
- 답하지 못하는 지점이 있으면 다음 커밋으로 가지 않고 그 자리에서 함께 본다. 그런 지점에 버그가 숨어 있는 경우가 많다.
- 등급 판단과 설명은 Claude가 하지만, 넘어갈지는 사용자가 정한다.

**커밋 크기**: A는 한 커밋에 상태 전이 하나. C는 묶어도 된다. 구현설계의 단계가 끝날 때마다 실제 실행 환경(로컬 서버, 테스트 서버, 실기기)에서 한 번 돌려 보고 다음 단계로 넘어간다. 단위 테스트만으로는 기존 경로·외부 서비스와의 맞물림을 확인할 수 없기 때문이다.

## 5. 커밋 (사용자가 요청할 때)

- 형식: `Feat: 주문 생성 API 추가`. 접두어는 `Feat`/`Fix`/`Test`/`Docs`/`Refactor`/`Chore`, 내용은 한국어. `Co-Authored-By` 줄은 넣지 않는다.
- 4.1의 커밋 크기로 나눈다. 리뷰와 되돌리기가 쉬워진다.
- DB 스키마가 바뀌면 배포 때 필요한 DB 작업을 {{기록 위치: 예) docs/db-changes.md 또는 PR 설명}}에 적는다. code-reviewer 공통 점검 5번도 같은 위치를 본다.

## 6. 합치기 준비 (요청 시)

합치기는 사용자가 결정한다. Claude는 준비까지만 한다.

1. 기본 브랜치를 최신으로 받아 기능 브랜치를 그 위로 옮긴다. 원격 기능 브랜치 강제 push는 사용자 확인을 받는다. 기본 브랜치는 rebase하거나 강제 push하지 않는다.
2. 충돌을 해결하고, 기본 브랜치 쪽 원래 변경이 그대로 남아 있는지 확인한다.
3. 테스트와 `review-loop`를 다시 실행한다.
4. PR 설명을 준비한다. 배포 시 필요한 DB 작업·환경변수는 따로 표시한다.
