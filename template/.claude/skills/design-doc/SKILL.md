# design-doc

설계 문서는 코드보다 먼저 쓰이므로, 틀린 전제가 그대로 구현으로 넘어간다. 그래서 문서의 모든 사실 주장은 코드(`파일:라인`)나 외부 출처(URL) 중 하나에 묶고, 묶을 수 없으면 `[가정]`으로 드러낸다.

## 실행 방식

| 역할 | 담당 |
| --- | --- |
| 코드 현황 조사 | `code-investigator` 에이전트 |
| 외부 자료 조사 | `external-researcher` 에이전트 |
| 작성, 결과 저장, 사용자 결정 받기 | 메인 세션 (사용자 결정과 이전 리뷰 맥락을 들고 있기 때문) |
| 사실 검증 | `review-loop` → `code-reviewer` |

두 조사는 대상이 달라 서로 확인할 일이 없으므로 백그라운드로 동시에 띄운다. 조사 에이전트는 파일을 쓰지 않고, 메인 세션이 결과를 `_workspace/<과제명>/`에 저장한다. 새 프로젝트라 코드가 아직 없으면 코드 조사는 건너뛴다.

## 0. 준비

- `_workspace/<과제명>/progress.md`를 만들거나 이어 읽는다.
- 기준 문서(`docs/01-product.md`, `docs/03-decisions.md`, 관련 이전 설계)를 읽는다. 이미 정해진 방향과 다른 설계를 새로 만들지 않기 위해서다.
- 조사 기준을 정한다. 원격이 있으면 `git -C {{저장소 절대경로}} fetch origin {{main}}` 후 `origin/{{main}}`, 원격이 없으면 로컬 `{{main}}`이다. 그 커밋 해시를 기록해 조사자에게 넘긴다. 작업 트리는 기능 브랜치일 수 있으므로 조사 기준은 항상 기본 브랜치다. 조사자는 fetch를 하지 않으므로 여기서 받지 않으면 오래된 코드로 설계하게 된다.
- 사용자 결정이 필요한 항목(기술 방식, 범위, 정책)은 조사 전에 묻는다. 결정 없이 쓰면 다시 REDO된다.

## 작성 모드

1. **조사 (동시)**: `code-investigator`에 조사 질문과 기준 커밋을, `external-researcher`에 외부 질문(연동 규격, 규제, 요금·제약)을 넘긴다. 결과는 `01-code.md`, `02-external.md`에 저장한다.
2. **작성**: `docs/02-design-template.md` 구조를 따른다. 개정이면 `v2`, `v3`처럼 새 파일로 쓰고 이전 판은 남긴다.
   - 코드 주장에는 `파일:라인`, 외부 사실에는 출처를 단다. 외부 사실은 조사자의 확인 수준을 넘겨 쓰지 않는다. "확인됨"만 단정문으로 쓰고, "추정"은 `[추정]`, 근거가 없으면 `[가정]`으로 표시해 "외부 확인 필요"에 올린다. 2차 출처의 추정이 사실처럼 구현으로 넘어가지 않게 하기 위해서다.
   - 조사 결과와 이전 판이 충돌하면 조사 결과를 따르고, 바뀐 이유를 "핵심 변경"에 적는다.
   - 개정이면 0장 "이전 판 반영"에 이전 리뷰 지적별 처리 결과와 위치를 적는다. 빠뜨린 지적이 다음 판까지 이어지지 않게 하기 위해서다.
   - 확정된 전제는 다시 논증하지 않는다. 독자가 이미 아는 내용이 결정할 내용을 가린다.
   - 기준 문서와 다르게 정해도 되는 것은 기술 구현 방식뿐이다. 기준 문서의 요구·정책을 바꿔야 하면 문서에서 바꾸지 않고 "결정 필요"로 올린다.
   - 제품 결정(범위, 정책, 요금, 문구)은 문서에서 정하지 않는다. "결정 필요" 표에 **선택지 / 개발 영향 / 결정 전 개발 기본값 / 개발 의견**으로 적는다. "개발 의견"은 위험·보안·기술 근거로 개발이 보는 사실과 의견(예: "이 검증 없이는 남의 데이터를 조회할 수 있다")이다. 제품 선택지 중 하나를 고르라는 권장은 사용자가 요청할 때만 따로 적는다. 결정 전에 권장이 섞이면 선택지의 영향을 덜 보고 고르게 되기 때문이다. 기술 구현 방식은 권장해도 된다.
   - 인증·결제·개인정보가 닿는 설계에는 위협별 대응표(위협 / 대응 / 위치)와 출시 전 보안 점검 목록을 둔다.
   - 구현 단계는 단계와 선행 관계로 적는다. 각 단계는 "끝나면 실제로 돌려 볼 수 있는" 단위로 자른다.
3. **사실 검증**: `review-loop`를 실행한다. 기준은 기준 문서, 이전 판, `01-code.md`, `02-external.md`, 사용자 결정 목록이다.
4. **보고**: 결정 필요 항목과 `[가정]` 목록을 사용자에게 먼저 보여 준다. 사용자가 정한 것은 `docs/03-decisions.md`에 남긴다.

## 재검토 모드

구현 착수 직전에 쓴다. **문서는 고치지 않는다.**

1. `code-investigator`를 대조 모드로 호출해 문서의 코드 주장을 하나씩 기본 브랜치와 대조한다. 외부 사실의 최신성이 쟁점이면 `external-researcher`도 함께 호출한다.
2. 결과를 `_workspace/<과제명>/audit.md`에 **맞음 / 어긋남 / 빠짐 / 확인 불가**로 정리한다. 어긋남·빠짐에는 근거와 문서 위치를 붙인다. 인증·결제·개인정보가 닿는 문서인데 위협별 대응표나 출시 전 보안 점검 목록이 없으면 "빠짐"으로 보고한다.
3. `review-loop`로 audit.md를 검증받는다. 대조 결과도 틀릴 수 있으므로 리뷰어가 "어긋남" 판정을 직접 코드로 재확인하게 한다. 그다음 사용자에게 보고하고 수정 여부를 묻는다.
