# harness-change

하네스는 저절로 자라지 않고, 몰래 바뀌면 어긋났을 때 되돌릴 수 없다. 그래서 언제 바꿀지(신호), 어디에 둘지(위치), 어떻게 남길지(절차)를 정해 둔다.

## 1. 변경을 제안하는 신호

다음이 보이면 작업 중이라도 사용자에게 하네스 변경을 제안한다. 어떤 신호인지, 어느 파일을 어떻게 바꿀지 한두 줄로 말한다.

- 사용자나 리뷰어가 같은 종류의 지적·교정을 두 번 이상 한다(작업이 달라도 종류가 같으면 해당). 같은 실수가 반복되면 개별 수정이 아니라 규칙이 빠져 있다는 뜻이다.
- 리뷰어가 개별 결과물이 아니라 하네스 자체의 빈틈(잘못된 절차, 빠진 규칙, 파일 간 모순)을 짚는다.
- 같은 절차를 세션마다 손으로 반복한다.

매 세션 지켜야 할 규칙과 절차는 자동 메모리에 저장하지 말고 하네스 변경으로 제안한다. 메모리에는 진행 중인 작업 상태와 개인 맥락만 둔다. 메모리에 쌓인 규칙은 세션마다 지켜진다는 보장이 없기 때문이다.

## 2. 규칙을 둘 위치

- **루트 CLAUDE.md는 짧게 유지한다.** 모든 세션에서 읽히므로 어떤 작업에서든 지켜야 하는 안전 규칙, 공통 절차, 라우팅만 둔다. 특정 작업에서만 필요한 규칙까지 쌓이면 컨텍스트를 차지하고 중요한 규칙이 묻힌다.
- 특정 작업에만 필요한 규칙은 그 작업을 맡는 스킬(`.claude/skills/<이름>/SKILL.md`)이나 에이전트(`.claude/agents/<이름>.md`)에 둔다. **실수가 생기는 지점**에 둬야 같은 실수를 막는다. 사실 조사에서 틀렸다면 문서를 쓰는 스킬이 아니라 조사 에이전트에 둔다.
- 같은 기준을 여러 파일에 둘 때는 한쪽에 다른 쪽을 가리키는 참조를 달아, 한쪽만 고쳐져 어긋나는 일을 줄인다.
- 스킬 없이 직접 쓰는 문서처럼 규칙이 닿지 않는 경로는 review-loop가 잡는다. 그 빈틈을 막겠다고 CLAUDE.md를 늘리지 않는다.
- 일반 개발 규범은 "알지만 시키지 않으면 건너뛰는 것"(테스트 실행, 동시성, 권한 확인 등)만 적는다. 모델이 알아서 하는 것(가독성, 네이밍)은 적어도 효과가 없고 중요한 규칙을 묻는다.

## 3. 구성 원칙

- 역할이 순서대로만 이어지면(작성 → 검증) 스킬 본문의 번호 순서로 서브에이전트를 차례로 호출한다. 서로 의존하지 않는 조사만 백그라운드로 동시에 띄운다. 역할이 3개 이상이고 진행 중 서로 교차 확인·토론이 필요할 때만 팀 모드를 검토한다. 팀 모드는 팀원 수만큼 통신 비용이 늘어난다.
- 에이전트는 `.claude/agents/`에 파일로 정의하고 `model`을 명시한다. 검토·조사 역할에는 Edit/Write를 주지 않는다.
- 에이전트를 늘리기 전에 병목을 본다. 혼자 개발할 때 병목은 대개 사용자가 이해하는 속도다.

## 4. 절차

1. **제안**: 신호, 바꿀 파일, 바꿀 내용을 사용자에게 말한다.
2. **승인**: 사용자 승인 없이 반영하지 않는다. 리뷰 지적으로 승인받은 범위가 바뀌면(예: 다른 파일로 옮기기) 다시 묻는다.
3. **반영**: 파일을 고친다. 규칙 문장에는 이유와 계기가 된 실제 사례를 짧게 붙인다. 이유가 있어야 애매한 상황에서도 취지대로 판단한다.
4. **검증**: `review-loop`로 PASS를 받는다. 리뷰어에게 이 스킬을 기준 자료로 넘긴다.
5. **커밋**: 루트 CLAUDE.md대로 사용자가 요청할 때 커밋한다. 한 커밋에는 한 가지 변경만 담고, 바꾼 파일 경로만 지정해 커밋한다(`git commit -m "..." -- <경로들>`). 다른 세션이 스테이징해 둔 파일이 섞이지 않게 하고, 규칙이 언제 왜 바뀌었는지 남겨야 어긋날 때 되돌릴 수 있다. 하네스는 코드와 같은 저장소에 있으므로, 기능 브랜치에서 작업 중이면 하네스 커밋이 기능 PR에 섞인다. 어느 브랜치에 커밋할지 사용자에게 묻는다.
